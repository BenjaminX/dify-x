Three Contracts · Turn “Good Enough” into Testable Conditions

Before launch, write three machine-executable contracts.

01 · TASK CONTRACTTask contract

Inputs, done condition, quality threshold, stop condition.

Missing → the system cannot know when it is done
02 · TOOL CONTRACTTool contract

Identity, access, budget, pre- and postconditions.

Missing → a suggestion becomes an unauthorized action
03 · EVIDENCE CONTRACTEvidence contract

Required input, source, action, version, and approval records.

Missing → only the final prose survives
Time 2:15. Core delivery: the task contract defines completion, the tool contract defines permission, and the evidence contract defines proof. Missing one produces wandering, overreach, or an unauditable run. Term: machine-executable means key conditions live in workflow configuration, tool schemas, or log fields—not only policy prose. Transition: first examine the context needed to understand the task. Evidence boundary: these contracts are a system-design abstraction, not three fixed Dify objects.
