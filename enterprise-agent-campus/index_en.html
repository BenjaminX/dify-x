Thesis · Start with Work, Not the Agent
DON'T START WITHHow autonomous is the model?

Capability alone cannot explain why a user would open the product.

→
START WITHWhat kind of work does it serve?

The work object, trigger, and deliverable shape the product.

Product form follows work form—not an autonomy ladder.
Time 1:30. Core delivery: the same model can become an IDE copilot, a service front door, or a background monitor. The difference comes from the work, not autonomy. Term: work form describes the object around which work persists, what triggers it, and how it ends. Transition: the first variable is the smallest unit of work. Evidence boundary: this is a research synthesis.

Four Questions · From Scenario to Product

Do not begin with a feature list. Answer four product questions.

01ENTRYWhere does the user meet it?

An existing app, a dedicated space, a service channel, or a system event.

02OBJECTWhat does the work persist around?

A current object, project, conversation, case, signal, or question.

03DELIVERYWhat does the user take away?

A suggestion, professional artifact, resolution, state change, alert, or decision.

04RHYTHMWhen do they return?

Every minute, project, request, event, or weekly business review.

Time 2:00. Core delivery: entry determines distribution, the work object determines state, the deliverable determines value, and rhythm determines whether the product persists. Term: usage rhythm is the natural recurrence of the scenario, not response latency. Transition: inspect six forms, each centered on scenario fit. Evidence boundary: the four questions support product discovery, not full requirements research.

When users know neither the answer nor the table, the product must carry the exploration.

Time 2:15. Core delivery: an analyst agent is not an NL-to-SQL box; it preserves the question, exploration branches, evidence, and decision artifact. It fits open-ended multi-step investigation. Term: consumable artifact means a notebook, chart, or memo that enters a business decision. Transition: complex projects can contain several agents, but that is usually an internal organization. Evidence boundary: OpenAI's system is bespoke and internal; platform scale is not agent adoption or accuracy.

Form Migration · Repetition Changes the Product

The agent did not “level up.” The work became systematic.

A user asks each timeAnalyst Agent→The same metric matters every dayMonitoring Agent
An expert gets help inside one documentCopilot→The corpus grows and the project lasts weeksWorkbench
A customer makes one requestService Agent→The request becomes a cross-system caseProcess Agent
MIGRATION SIGNALS: repetition · persistent state · cross-role / cross-system · stable deliverable
Time 2:00. Core delivery: migration comes from repetition, accumulated state, and cross-system expansion. Analysis becomes monitoring, local assistance becomes a workbench, and one service request becomes a process case. Term: form migration often adds a layer rather than replacing the old product. Transition: Dify lets one capability be packaged into different entry points. Evidence boundary: common pattern, not a required evolution path.

Q&A · Infer the Product from the Scenario

Do not say “I want to build an agent.”
Ask which product form the work requires.

01 What is the smallest work unit in your scenario?

02 Where does the user meet it, and what do they take away?

03 Is it on-demand, project-based, or continuously running?
